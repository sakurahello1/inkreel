# 场记 · 架构说明

## 分层

```
src/
  lib/           前后端共享的类型与状态常量
  components/    通用 UI 原子（Button / Stamp / Placeholder…）
  app/           页面与客户端组件
  server/
    core/        与业务无关的骨架：Job 基类、ImageJob 模板、RefBuilder
    providers/   外部模型接口：chat / image / video / minimax / sse
    services/    业务逻辑，不依赖 Next，可单独测试
    jobs/        后台任务，一个任务一个文件
    agent/       拆镜与改写的提示词工程
    lineage.ts   输入指纹与新鲜度
    queries.ts   读模型：把 Prisma 行拼成页面要的视图
    actions.ts   Next server action 门面（很薄）
    ffmpeg.ts    导出流水线
```

依赖方向是单向的：`app → actions → services → jobs/providers → db`。
`services` 不 import Next 的任何东西，`core` 不 import 任何业务模块。

## 三个关键设计

### 1. 输入指纹决定「过期」，而不是传播标记

每个产物在生成的那一刻，把它用到的**全部输入**压成一个哈希存进
`Unit.sheetInputHash` / `Shot.frameInputHash` / `Shot.videoInputHash`。
任何时候重算一遍，对不上就是过期。

为什么不用「上游改了就逐级标记下游」：那种传播逻辑只要漏掉一条路径，
就会长期沉默地错下去，而且改回原值也不会自动恢复。重算指纹永远反映当下真相，
把提示词改回去，过期标记会自己消失。

指纹的输入构成见 `lineage.ts`。整章算一遍约 15 毫秒（一次性加载上下文，不逐镜查库）。

### 2. 出图任务用模板方法，流程只写一次

人物三视图、道具概念图、镜头首帧，流程完全相同：

```
装载实体 → 装配参考图 → 拼提示词 → 建生成记录 → 调 gpt-image-2 →
存产物 → 事务里同时更新实体与生成记录 → 出错则两边一起标失败
```

这套流程写在 `core/image-job.ts` 的 `ImageJob` 基类里，四个子类只填不同的那几块。
以前这段在四个地方各抄一遍，加血缘指纹时就漏改过一处。

参考图的装配用 `core/refs.ts` 的 `RefBuilder`：图和它的名字必须严格同序
（提示词里那句「参考图依次为：…」靠顺序绑定身份），以前是两个数组手动 push，容易错位。

### 3. Generation 表就是版本历史

每次生成都留一整条记录：提示词、参数、输入血缘、产物资产、花费、耗时。
`VersionService` 把它当版本库用——回看任意历史版本、把旧版设回当前（只改指针不花钱）、
从任意一级往下重跑。界面上就是右栏每个阶段下面那条「历史版本」。

## 生产管线

```
人设图 ┐
道具图 ├──────→ 首帧 ──→ 视频 ──→ 成片片段
画风   ┘         ↑        ↑
             首帧提示词  视频提示词 + BGM
```

拓扑是固定的。「展开为画布」把这张图摊平给人看，标出每一级的新鲜度，
但不提供任意连线——那需要图执行引擎，成本翻十倍而实际用不到。

## 容易踩的坑

- **改了 `jobs/` 或它依赖的 `ffmpeg.ts`、`lineage.ts` 之后必须重启 dev server。**
  任务处理器在模块导入时注册到 runner，Next 的热更新会重新编译文件，
  但 runner 手里握的仍是旧闭包。改页面和 server action 则不用重启。
- 数据库与存储在项目目录之外（`G:\short-play-data\`）。放在项目里会让
  Next 的文件监视器在每次任务写盘时触发 Fast Refresh，打断正在跑的 server action。
- exFAT 分区上跑 `next build` 会报 `EISDIR: readlink`，要在 NTFS 或 Docker 里构建。
